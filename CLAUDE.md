# FPheLp

Automates a private FPL league owner's group communications — standings, results, money pot — instead of them posting by hand. Owner-only; league members never log in.

See [ROADMAP.md](./ROADMAP.md) for scope, [ARCHITECTURE.md](./ARCHITECTURE.md) for design, and [SECURITY.md](./SECURITY.md) for what is defended and what is knowingly accepted.

> **The endpoint shapes in ARCHITECTURE.md are confirmed against a finished gameweek**, not taken on trust: GW1 was scored on 25 Aug 2026 and its payloads are recorded in `src/lib/fpl/recorded/`, anonymised as they were recorded. `recorded.test.ts` parses them through the real functions on every `npm test`, so a shape change fails the suite instead of a send. Read [docs/GW1-VERIFICATION.md](./docs/GW1-VERIFICATION.md) before writing code that depends on API shapes — it is the evidence behind the gotchas below, and a season opener does not come round again.

## Stack

TypeScript / Node 24, **Next.js 16.3 (App Router) + React 19.2**, Postgres + Drizzle on Railway, Resend for email, Vitest + Playwright.

UI is Tailwind v4 over the design tokens in `src/app/globals.css`, used through the shared primitives in `src/components/ui.tsx`. Components should not reach for raw palette classes (`neutral-300`, `dark:neutral-700`): those were duplicated across every file and made dark mode something each one re-derived by hand.

Brand colours live in the logo, not in the tokens: the gradient runs cyan `#0399ec` → blue `#2762e1` → purple `#991ce1`. The UI palette stays neutral on purpose, so the mark is the only saturated thing on screen.

**Tailwind v4 dropped Preflight's `cursor: pointer` on `<button>`.** The `Button` primitive sets it; a hand-rolled `<button>` will silently have the wrong cursor.

**Read [AGENTS.md](./AGENTS.md) before writing Next.js code.** Next 16 has breaking changes from earlier versions; the bundled docs in `node_modules/next/dist/docs/` are authoritative over recalled API knowledge. That file is regenerated by `next dev`, so leave it committed.

## Commands

- `npm run dev` — local dev server
- `npm run build` / `npm start` — production build and serve
- `npm run lint` — ESLint
- `npm run db:migrate` — applies pending migrations to **whatever `DATABASE_URL` names**, which locally is the `fphelp_dev` in `.env`. Run it after `npm run db:generate`, or a new table exists only in the schema file and the page that queries it throws `relation "..." does not exist`. `npm run e2e:db` migrates `fphelp_e2e` **only** — it is not this step. Production is migrated by the deploy, not from here: `railway.json` sets `preDeployCommand` to this same script, so it runs on Railway with that service's own `DATABASE_URL` before the new app starts. That shared use is why the script carries **no local-host guard** like `e2e/support/db-url.ts` — one would break every deploy. What keeps it local is `.env` pointing at `localhost`; check that before running it anywhere unfamiliar
- `npm run db:clear-digest -- --gw N` — deletes one gameweek's digest, messages and deliveries for the reference league. Dry run without `--confirm`. Manual only, never a deploy hook — it removes the owner's own writing. See [docs/GW1-VERIFICATION.md](./docs/GW1-VERIFICATION.md) §6b.
- `npm test` — Vitest, the pure computation layer
- `npm run e2e:db` — creates and migrates `fphelp_e2e`. Run once, and again when migrations change
- `npm run e2e` — Playwright. Builds the app into `.next-e2e` and serves it, so it does not take port 3000 from a `next dev` you have running. **It does not isolate that server, and running both at once corrupts it** — see the build/dev collision under Gotchas
- `npm run e2e:screens` — screenshots of every page in both themes into `test-results/screens/`. Asserts nothing; it is for looking at
- `npm run build:logo` — regenerates the logo variants and icons from `assets/logo_original.png`. Manual; the outputs are committed
- `npm run fpl:record` — overwrites `src/lib/fpl/recorded/*.json` with the live API's current bytes, the fixtures `recorded.test.ts` checks the parsers against. **Only meaningful on a settled gameweek** — check `fpl:snapshot` reports `statsReady: true` first, or you bake a provisional payload in and the send gate's ready path stops being tested. Outputs are committed; `bootstrap-static` keeps only `events`, since the other ~1 MB is players and teams this app never reads
- `npm run fpl:snapshot` — prints what the live FPL API says right now, through the app's own client: the send gate's verdict, both standings collections, and the computed league average against FPL's global one. Read-only, no database. This is how [docs/GW1-VERIFICATION.md](./docs/GW1-VERIFICATION.md) §2/§3/§5 get checked, and the moments worth checking do not repeat

Deployment is Railway (project `fphelp`, in the owner's personal workspace), with two services from this repo plus Postgres:

| Service | What it is |
| --- | --- |
| `fphelp-app` | The web app. The one with a public domain, and the one `railway logs` / `railway ssh` usually mean |
| `cron-capture-history` | Cron only, no domain. Runs `npm run job:capture` hourly, Sunday–Wednesday (`0 * * * 0-3` UTC). See ARCHITECTURE.md "Cron service configuration" |

Services are named for **what they do**, not for the project — the project already provides that. New scheduled jobs get their own `cron-<job>` service rather than being added to this one, so the dashboard says which job is failing. Phase 3's deadline reminders will be the second.

## Monitoring

Sentry, server-side only, **entirely optional** — no `SENTRY_DSN` means the SDK never initialises and every call no-ops, so local dev and both test suites need no configuration. `next.config.ts` skips `withSentryConfig` unless `SENTRY_AUTH_TOKEN` is set, so builds work without credentials. Don't make either one required.

The Sentry org and project are **literals in `next.config.ts`**, deliberately — they are slugs, not secrets, and the token is the only credential worth keeping in the environment. If the project is renamed in Sentry, update that literal: the DSN keeps working regardless (it is keyed on the numeric project ID), so the only symptom is source maps silently ceasing to upload.

The cron's Sentry check-in **upserts its own schedule** (`monitorConfig` in `scripts/capture-history.mts`, currently `0 * * * 0-3`). Change the Railway cron and you must change that string too, or the monitor alarms every Thursday when the job correctly isn't running. See ARCHITECTURE.md "Monitoring".

## Conventions

- Digest computation is **pure functions over fetched JSON**. Keep fetching, computing, and rendering separate; the computation layer is where the tests live.
- FPL API responses are captured as **recorded fixtures** for tests. The API is unofficial and shifts between seasons — the recordings are the change detector. `src/lib/fpl/recorded/*.json` holds the real bytes from a settled GW1 (25 Aug 2026), and `recorded.test.ts` parses them through the real functions on every run, so a shape change fails `npm test` instead of a send. Re-record with `npm run fpl:record`, and **read the diff before adapting the parsers — the diff is the finding**.
- **The recordings and `fixtures.ts` cover different halves, and neither replaces the other.** Recordings prove the app can read what FPL actually sends; the hand-authored fixtures prove it renders correctly given cases the real league does not contain — a tie at the top, a manager with no scores yet, and standings past one page. The reference league is 17 managers on a single page, so `has_next` is false in every recorded payload and pagination is only exercised by the fixture, which pages at 10.
- **The recordings are anonymised as they are recorded**, by `scripts/anonymise.mts`, which `npm run fpl:record` calls before anything reaches disk. Names, team names, entry IDs, the league's ID and name, and the uploaded-badge URLs are substituted; shape, types, key order and the pagination envelope are not. The mapping is deterministic, so a re-record diffs against the last one on what the API changed rather than on which invented name each manager got. Never commit a recording taken any other way.
- **End-to-end tests never call the real FPL API.** `FPL_FIXTURES=1` swaps the client's `fetchImpl` for a canned one. The suite also truncates every table, so it refuses any database that is not named `fphelp_e2e` **and** on a local host — the name alone would let a remote database with the right name through, and there is deliberately no override.
- One template renders both the HTML email and the plaintext WhatsApp payload.

- **Setup's three tabs are split by save model, not by topic.** Pot & prizes batches behind Save; Communication and People write on every click. Adding a section means deciding which of those it is, and putting it in the matching panel. The panels are **kept mounted and hidden** rather than unmounted, so a switch cannot discard the money form's unsaved edits — `?tab=` is kept in step with `replaceState` for the same reason, since a real navigation would remount. Any e2e test touching a non-default panel has to open its tab first.

- **"Manager" means an FPL entry** competing in the league (`managers` table). A person who logs in here is an **owner** (`users` + `league_users`). Don't conflate them.

## Gotchas

These are the traps that produce silently wrong output rather than errors:

- **Never run `npm run build` or `npm run e2e` while `npm run dev` is up.** `NEXT_DIST_DIR` relocates the build output but **not** the generated types: both commands write `.next/dev/types/` regardless, so the `.next-e2e` trick keeps them off port 3000 and does nothing to stop them racing on that directory. The loser is a file with a duplicated, truncated block, and the damage lands two places that both point away from the cause — `tsconfig.json` includes `.next/dev/types/**/*.ts`, so `tsc` and `next build` start failing on line numbers inside generated code nobody wrote; and the dev server is left with an incomplete route table, so **every dynamic route 404s as though it had never existed**. Observed 2026-09-07: `/l/<any id>/send` returned the app's own "Nothing here" page while `/leagues` and `/signin` served fine, and `app-paths-manifest.json` listed no `/l/[leagueId]` entries at all. The fix is `Remove-Item -Recurse -Force .next` with the dev server stopped, then restart it — the branch is not broken and no code change will help.

- **League average must be computed** as the mean of `event_total` across standings results. `events[].average_entry_score` is the *global* FPL average — using it looks fine and is wrong.
- **`standings.results` is paginated.** Follow `has_next` / `?page_standings=N` or managers past 50 vanish from the digest.
- **`new_entries` is an object, not an array** — `{has_next, page, results}`, same envelope as standings, paginated separately. Its managers are invisible in standings until the next GW processes: pre-season the real league had **0 standings rows and 14 new entries**.
- **`new_entries` elements have a different shape** — `player_first_name`/`player_last_name` instead of `player_name`, and no score fields at all. Normalise both into one internal type, dedupe on `entry`, and handle "manager with no scores yet".
- **`finished` ≠ safe to send.** It flips before bonus points apply. Gate on `event-status` (all `bonus_added`, `leagues === "Updated"`) cross-checked with `data_checked`.
- **`finished: false` does not mean nobody has scored.** During the first gameweek of a season nothing has finished *and* every manager already has a provisional total, so `lastFinishedGameweek() === null` covers two opposite states. `sendGate` separates them with `liveGameweek()`; treating the null as pre-season let the composer offer a mid-match table with no warning. Observed on 2026-08-21: scores were in and `bonus_added` was still `false` hours later. The gap is not cosmetic — the league average moved 52.82 → 53.65 between the last provisional snapshot (24 Aug 23:54Z) and the final one (25 Aug 14:14Z), with no fixtures left to play. A digest sent on the earlier reading would have published wrong totals to the whole league.
- **`event-status.leagues` is not a two-state flag, and `""` does not mean "no gameweek".** Observed values: `""`, `"Updating"` (2026-08-21, mid-GW1) and `"Updated"` (confirmed 2026-08-25, once GW1 went final). `""` is not "before a gameweek" as first recorded — it was the value all through 24 Aug with GW1 live and 17 managers scored, so it means "not currently recalculating", which covers both pre-season and a live-but-idle gameweek. Compare with `===`; a truthiness test opens the gate mid-gameweek, and an emptiness test misreads a live one as pre-season.
- **`status[].points` is three-valued too**: `""` before a day is played, `"p"` while its points are provisional, `"r"` once they are final (confirmed 2026-08-25). Nothing reads it — the gate uses `bonus_added` — but it tracks the same transition and is the field to check when `bonus_added` looks wrong.
- **`event-status` returns `status: []` outside a live gameweek**, and `[].every(...)` is `true`. Require `status.length > 0` first or the gate opens on nothing.
- **Never put a phone number in the WhatsApp link.** `wa.me/<number>?text=` opens an individual chat and makes groups unreachable — it still looks like a working link. Always `whatsapp://send?text=` / `https://wa.me/?text=` with no number.
- **Digest length budget: ~1,500 chars URL-encoded.** Newlines cost `%0A`; table padding is pure cost. The composer must show this live as blocks are toggled — standings alone can eat most of it.
- **`digests` stores structured stats, not rendered text.** Blocks are toggled per message, so rendering happens at send time from the stored JSON. Store the owner's final `sent_text` separately — once edited, it isn't reproducible from the API.
- **The app never sends on the owner's behalf.** It prepares a draft; the owner writes, composes and taps. There is no automatic cadence.
- **Delivery must be idempotent** — `deliveries` is unique on `(league_id, gameweek, kind)`. Cron and manual send can both reach prepare.
- **Delivery is never "confirmed".** `prepared` → optionally `marked sent`; a null `sent_at` means unknown, not failed.
- **Idempotency is on `digests`, not `messages`.** `digests` is unique per `(league_id, gameweek)` so polling can't double-prepare; `messages` is deliberately many-per-gameweek, since the owner may send a follow-up. Never add `user_id` to the digest key — co-owners share one digest and one visible sent/draft state.
- **An unset pot is not a pot of zero.** `leagues.pot_total` is nullable and `LeagueSettings.potTotal` is `number | undefined`, because a league is handed over before anyone has counted the money — members are still joining and paying. Collapsing that to `0` makes Setup greet its new owner with `fixed-exceeds-pot` and a disabled Save, and makes the digest tell the league its pot is `$0.00`. `computePot` reports `potSet`; nothing renders a pot figure without checking it. The fixed prizes still render, since they are amounts per winner rather than shares of a total.
- **Fixed prizes and league expenses come off the top; percentages apply to the remainder.** `remainder = pot − (gw_winner × gameweeks) − season_best_gw − expenses`, then top-6 percentages apply to `remainder`. Applying them to the whole pot over-commits it and only surfaces at season end. Re-validate on every pot edit.
- **An expense can tip a league over when the prizes alone fit.** `league_expenses` joins `committed_fixed` in the `fixed-exceeds-pot` check, which is why expenses are part of `LeagueSettings` and save behind Setup's Save button rather than per-click like the owners and recipients lists — the pot, the fixed prizes and the costs are one set and are validated together. `saveSettings` rewrites the rows wholesale inside the same transaction as `prize_rules`, so a stale row cannot survive as a deduction nobody entered. Order comes from `position`, never `created_at`: one bulk insert stamps every row the same instant.
- **The digest prints each expense as a negative line, and hides them all when the pot is unset.** `Pot  $1,800.00` then `Trophy engraving  -$100.00` — without the deduction the prizes below stop adding up to the pot above, and a league of eighteen will do that arithmetic. The minus sign carries it rather than a "Less" prefix, which would push the label out of a right-aligned column. With no pot the lines go too, for the same reason the pot line does: a subtraction with nothing to subtract from. Three renderers must agree, so they share `prizeRows` — `renderPrizeStructure`, `renderPrizeHtml` and email's plaintext branch.
- **The prize figures only align in a monospace context.** WhatsApp renders everything outside a ``` block in a proportional font, where padded columns do not line up and the padding is budget spent on nothing — so the block carries its own fences, and the paid places go two to a line to pay for them (~90 encoded characters more than the unaligned version, on a ~1,500 budget). Plaintext email uses the same padding without the fences, which are WhatsApp markup and would read as literal backticks. HTML email uses a real table instead and needs neither.
- **Take the gameweek count from `events.length`**, never hardcode 38.
- **Rank and best-GW winnings are `provisional`** until the final GW is scored. Only GW-winner amounts are final as they accrue. Never render a provisional figure as settled.
- **Ties pool and split**: N managers tied at rank R take positions R…R+N−1, pool those prizes, divide equally. Paying each tied manager in full overdraws the pot.
- **Paid places are configurable** — N is just the number of `season_rank_pct` rows. Validate contiguous ranks from 1 and percentages summing to 100%. Use decimals, and derive the last place as `remainder − sum(others)` so rounding can't miss the pot.
- **Prize rules lock once the ledger is finalised.** Editing them mid-season only moves provisional projections; editing after season end rewrites settled `winnings` rows.
- **Detect ties on `rank`, not `rank_sort`.** `rank_sort` imposes an arbitrary total order that makes a real tie look resolved; it's only for deciding where a rounding remainder lands.
- **Auth.js `pages` entries must not carry a query string.** Auth.js appends its own parameters with `?` unconditionally, so `verifyRequest: '/signin?sent=1'` produces `/signin?sent=1?provider=resend&type=email` — two `?` in one URL, with `sent` parsing as `1?provider=resend`. It looks like it works, because a truthiness check on that value still passes. The page reads `provider`, which Auth.js always supplies, instead of a flag we cannot attach.
- **Sign-in is rate limited in two places, with two keys, and both are load-bearing.** `/signin`'s Server Action limits before calling `signIn` — that is where the readable "Too many sign-in requests" message comes from, and it runs **before the allowlist** on purpose: limiting only after would make a rate-limit response something only a real owner's address could produce, which is a second enumeration oracle on a page that already has one. `sendVerificationRequest` in `src/auth.ts` limits again, and that is the check that actually holds, because Auth.js publishes `/api/auth/signin/resend` and a POST straight to it never touches the Server Action. The keys differ (`signin:form:` and `signin:send:`) **deliberately**: sharing one would count every form submission twice, halving the limit for the only people who use the form. Counters are in-memory (`src/lib/rate-limit.ts`), which assumes **one container** — scale past that and each instance counts separately, which fails open. That is the day it moves to Postgres.
- **A link preview will spend a sign-in link before the owner does.** Magic-link URLs are single-use, and every chat app fetches a URL to build its preview card — that fetch verifies the token, consumes it, and takes the session. The owner's tap then arrives second and gets `error=Verification`, which reads as "auth is broken" and isn't. Confirmed on 2026-08-17: `WhatsApp/2.23.20.0` in the Railway HTTP logs, 3–8 seconds ahead of the owner's iPhone, three times. `railway logs --http` and its `clientUa` field is how to tell; see README "Deleting sessions".
- **Membership is never granted by visiting a page.** `findMembership` is read-only and the pages refuse a non-member; the link is created only by `scripts/bootstrap-owner.mts`, `scripts/add-owner.mts`, or an existing owner using the owners list in `/setup`. The predecessor auto-enrolled on first visit, which made loading `/setup` the act that conferred ownership.
- **`users.can_create_leagues` is what keeps the allowlist from going transitive.** Being in `users` is the sign-in allowlist, and `addOwner` creates that row as a side effect of adding a co-owner — unavoidable, since a co-owner who cannot sign in is useless. Once creating a league became a UI action, that side effect would otherwise mean anyone an owner invites can start their own league and invite others, so "vouched for by the operator" becomes "vouched for by someone they vouched for". The flag defaults to **false** and is granted only by `scripts/add-owner.mts`, which needs production shell access. It is not `role` — `role` is per-league and grants nothing; this is a property of the person and governs exactly one action.
- **`/` routes, `/leagues` is the list.** `/` sends an owner with one league to their composer and everyone else to `/leagues`. The split exists because the redirect would otherwise leave a creator with exactly one league unable to reach the create form. The nav mark points at `/leagues` for the same reason — pointing it at `/` would make it a no-op from inside your only league.
- **Creating a league is two steps and re-fetches the name.** Look up, echo back name and manager count, then confirm — `fpl_league_id` is unique so a claim is first-come and awkward to undo. The name is fetched again server-side rather than accepted from the client: a Server Action is a public endpoint, and storing what it posts would let a league be created under any label, including one impersonating another league. Both steps re-check the flag, since the button being absent proves nothing about what was posted.
- **The league comes from the URL, and resolving it never creates anything.** Pages live at `/l/<fplLeagueId>/{send,setup,dues}` and go through `requireLeagueAccess` in `src/lib/league-access.ts` — the one place a league URL is interpreted. It looks the league up, it does not `ensureLeague` it: that ran on every page load while the ID came from the environment, and from a URL segment it would let anyone mint a league row by typing a number in the address bar. An unknown ID is a 404; a real league you don't own is `NotAnOwner`, which says who can fix it. The segment is the **FPL numeric ID**, not the internal UUID — the number the owner already knows, and the one Setup prints. Bare `/send`, `/setup`, `/dues` still exist as redirects for an owner with one league; `/` is the chooser.
- **The nav belongs to whoever can vouch for the league, and the root layout renders none.** `src/app/l/[leagueId]/layout.tsx` draws it for a real league, `/` draws the reduced bar (mark and Sign out only), and `/signin` and the 404 get nothing. `Nav`'s `prefix` is **given, never derived**: it briefly read the league out of `usePathname`, which is wrong in exactly the case that matters — on a 404 the path still contains `/l/424242/`, so the bar offered three links into a league that does not exist, each a further 404. The pathname says what was *asked for*; only the server knows whether it resolved. `prefix = null` also covers the non-member, whose links would all refuse them. `who` is passed on both branches so a refusal is not a dead end with no way to sign out.
- **`not-found.tsx` lives at the app root and must not be added under `l/[leagueId]/`.** A boundary inside that segment renders *inside* the league layout, which is the bug above rebuilt. Keeping the only boundary at the root is what makes a bad league ID fall out of the league chrome entirely. One consequence to expect: `notFound()` is thrown from the layout mid-stream, so the 404's markup arrives in the RSC payload rather than the initial HTML — the status is still 404 and the rendered page is correct, but a raw `curl | grep` will not find its text.
- **Nothing else writes `leagues.name`, so `syncLeagueName` has to.** `ensureLeague` was keeping it current as a side effect of resolution. The three pages that fetch standings call it, and it no-ops unless the name changed. Skip it on a new page and a league created by `add-owner.mts` keeps the placeholder "FPL league" in the chooser forever.
- **The capture cron covers every league, and the gate is what keeps that affordable.** It iterates the `leagues` table, so `FPL_LEAGUE_ID` no longer affects a running deployment at all — only what a script does when you don't name a league. The run asks `gameweekGate` **once** from the two global calls (`bootstrap-static`, `event-status`) and returns before touching any league if no gameweek has settled: a skipped poll costs 2 FPL calls whether there is one league or fifty, which matters because ~95 runs in 96 skip and the API blocks on reputation. Only a ready gate pays the per-league cost of standings plus one call per manager.
- **A skipped poll no longer refreshes rosters.** `upsertManagers` used to run hourly off a standings call the gate now avoids, so `managers` is written when a gameweek settles rather than within the hour of someone joining. Nothing user-facing reads that table — pages build the roster live from standings — and recording who was in the league *at capture time* is its actual job.
- **A run has a wall-clock budget (`RUN_BUDGET_MS`, 2 minutes) and stops starting new leagues past it.** Leagues it did not reach are reported `deferred` and taken by the next poll, which is safe only because a league with fewer stored entries than its roster reads as outstanding again — the same property that makes a partial capture self-healing. Leagues are ordered oldest-first, so the long-established league is never the one deferred.
- **A block aborts the whole run, not just that league.** `FplBlockedError` is per-IP — confirmed 2026-09-01, when all four endpoints refused this host at once — so continuing would spend the run hammering an API that is already refusing us. Rows collected before the block are saved, never discarded.
- **Any league failing makes the run an error**, which is what the non-2xx and the failed Sentry check-in mean. A league that cannot be captured is losing history that cannot be backfilled once a manager leaves; that must not hide behind nine successes. A `deferred` league is *not* a failure. **The known false alarm** is a manager whose history fails permanently — a deleted FPL account — which stalls that league below its roster target, so it re-captures every poll *and* fails the check-in every hour, unclearable. See ROADMAP Phase 1; the fix needs a "known unobtainable" mark the schema does not have yet.
- **Adding an owner writes two rows, and removing one deletes only the second.** `users` is what `src/auth.ts` allowlists for sign-in; `league_users` is what every page and action checks. Removal drops the membership and keeps the user, because `messages.created_by` and `deliveries.sent_by` are `set null` — deleting the account would erase who sent past digests. A removed owner can still sign in, and correctly lands on "not an owner".
- **`role` grants nothing in v1.** It's stored for future permission work; every owner can do everything, including send.
- **The FPL invite code is not the league ID.** `1xrliv` is a join code; the API needs the number from the league URL, and there's no unauthenticated way to convert one to the other.
- **FPL sits behind Cloudflare** and blocks many datacenter IPs. Don't move to serverless with rotating egress. Cloudflare is a constraint we're subject to, not a vendor we use — Railway is the only host.
- **Email recipients go in `bcc` or `cc`, never `to`.** `to` carries the sender alone, so the message always has a valid addressee. Which of the other two is the owner's choice, stored as `leagues.hide_recipients`, editable from both Setup and the composer's email tab, and defaulting to hiding: `bcc` discloses nothing but makes reply-all impossible, and `cc` publishes every address to every member — irreversibly, on the first send — which is the only way a league can hold a conversation over its own digest. **`cc` cannot be batched:** batching is invisible under `bcc`, but under `cc` it splits the league into groups that can't see each other, so `sendEmail` refuses above 50 rather than fragmenting the thread silently.
- **`AUTH_EMAIL_FROM` has no fallback for digests**, unlike sign-in mail which falls back to `onboarding@resend.dev`. A digest arriving from a stranger's address, to members who never signed up, is worse than not sending — so it fails instead.
- **The email is re-rendered server-side from the stored digest**, never sent from HTML the browser supplies. A Server Action is a public endpoint; accepting markup would mean mailing the league something we never saw, with `renderEmail`'s escaping bypassed.
- **A send failure has two audiences.** `error` is the owner's sentence, `detail` is the provider's words for the `deliveries` row and the log. Never let a cause sentence assert scope ("nothing was sent") — a later batch failing makes it a lie, and the owner resends to people who already have it.
- **Email needs a recipient list; WhatsApp doesn't.** The API gives no addresses, so `recipients` is owner-maintained and drifts from `managers`. Email is opt-in per league.
